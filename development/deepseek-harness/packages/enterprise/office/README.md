# @deepseek-ai/dsh-enterprise-office

English | [中文](README.zh.md)

## Summary

Create employee tasks, to-dos and same-day meetings, invite coworkers and retain their replies across restarts. Assignees and invitees receive durable inbox entries. Authorized employees can change work status and edit their contact details; administrators manage membership and read audit records. Use this package behind a trusted employee authentication adapter. It does not authenticate a browser or replace Agent sessions, permissions or scheduled prompts.

See the [Drive-reader reference](drive-readers/README.md) for optional image, authorized knowledge and Office delivery-check configuration, authority, retention and limitations.

## Use this package

Administrators may enable first-password invitations for existing active members with `memberInvites: { maxTtlMs: 3600000, maxEntries: 1000, maxBytes: 1048576 }`. All three positive safe-integer limits are required; omission keeps invitations disabled and does not open their domain. After reviewing the member's current role and expiry, `issueMemberInvite` returns a code once for the administrator to copy and deliver privately. Exact retries with the same issuance `requestId` return metadata only; a lost code requires an explicit new issuance, which revokes the previous code in the same commit. The service does not send email or external messages.

The recipient submits the code and a 15–1024-character first password through the employee Host. `acceptMemberInvite` derives the target from the code, rechecks expiry, revocation, current issuer authority and the target's active role after hashing, and commits only the target's first credential in the existing identity v1 domain. An existing credential makes every code for that member unavailable, including after restart; invitation acceptance cannot reset a password. The identity audit retains its existing `credential_set` action with the target as actor. Success returns only `memberId`, creates no session and leaves normal sign-in as a separate step. Administrator `memberInvite` views expose independent current credential, expiry, revocation and review facts without a secret or a claimed acceptance timestamp; `revokeMemberInvite` does not remove an already-set password.

Back up `enterprise_office_member_invites` together with the original employee directory and `enterprise_office_identity` from one consistent stopped-service snapshot. Its independent v1 ledger contains issuance and revocation metadata, request fingerprints and SHA-256 code hashes; raw codes and passwords are never stored there. Acceptance uses one identity commit and does not add a second consumed marker. Restoring an older credential snapshot may therefore make a retained code usable again; revoke outstanding codes before reopening an inconsistent recovery. All retained rows count toward the explicit entry and complete compact UTF-8 global-JSON byte limits, with no automatic pruning. Capacity exhaustion preserves existing data and retry receipts; lowering limits below retained size can reject subsequent mutations. Existing Office, identity and Native schemas remain unchanged.

Private customization requests persist system or skill name, contact person and requirements without an external delivery channel. `customizationMaxOperations` defaults to 1,000 immutable save receipts and `customizationMaxBytes` to 16 MiB of complete UTF-8 domain JSON; reaching either bound rejects new saves and retains original retry receipts. Include `enterprise_office_customizations` and the original employee directory in backups. Metadata pages omit contact and requirement bodies; details and edits remain owner-only, including for administrators. The [employee UI](../../client/ui-office/README.md#use-this-package) owns reviewed export and conflict recovery.

Work creators and administrators can confirm archive, recycle-bin deletion and restoration using `changeWorkLifecycle` with an explanation and reviewed revision. Assignment alone grants no lifecycle authority. `view.items` and daily counts include active work; `view.inactiveWork` contains only authorized archived/recycle-bin records. Inactive work rejects active item reads and mutations, while authorized attachment downloads remain available under current Drive permissions. Restoration preserves item identity, status, assignment, deadlines, checklists, files and business history, but requires delivery resubmission. Changes atomically retain lifecycle history, recipient notices with the item title, and audit. Files and Native Sessions are retained. Follow the [lifecycle upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-work-lifecycle/guide.md) before shared deployment.

Work attachments retain up to 20 distinct reviewed Drive versions. The item creator, current assignee or administrator replaces references using the reviewed item revision; unchanged retained references need no new Drive grant. New or changed references require current file access and version. Linking never copies bytes or changes Drive permissions. `workAttachments` withholds names and metadata for inaccessible or replaced versions; `workAttachmentInfo` verifies both current item/file access and stored bytes before download. Removal preserves the source file. Changes atomically commit `work_attachments_updated` notices and audit and invalidate pending deliveries. Delivery submission and confirmation require current access to all reviewed versions; return remains available. Follow the [attachment upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-work-attachments/guide.md) before editing shared data.

The seed applies only to an uninitialized domain. Restarting with a different seed does not overwrite existing company data or members. Subsequent membership changes require an active administrator through `saveMember`. An adapter must authenticate the employee before passing an actor id; accepting an arbitrary browser-supplied actor id is unsafe.

Pass `null` as the third `saveMember` argument when creating an identity; an existing ID returns `conflict`, including for inactive members. For an edit, pass the previously reviewed member record. The service compares its fields inside the commit queue and rejects stale changes without changing business data or its audit. Omitting this argument preserves trusted adapter upserts. The final active administrator cannot be removed or demoted. Only administrator views contain `managedMembers`, including inactive identities; the ordinary `members` directory contains active employees only.

Reactivation first removes the employee's retained sign-in sessions. Its durable `session_revoked` entry identifies the requesting administrator as actor and the employee as target. Identity and membership use separate commits: if the subsequent member save fails, the employee remains inactive and the completed revocation stays recorded.

Active administrators call `auditPage` or `auditExport` through the authenticated office request API. Both take an explicit `limit` of 1–100 and `before: null` for the first batch; use the returned `next` for older entries. Optional exact filters select `source`, `actorId`, `targetId`, `action` and inclusive Unix-millisecond `since`/`until` timestamps. Sources cover business changes, identity, organization, Drive, integration imports, saved connections and `request_denial`. Records expose only source, revision, actor, action, target and time; request denials additionally expose their safe `denialCode`. `auditExport` returns NDJSON content with count, total and continuation, without credential fields, business content or connection configuration. Each page and export batch rechecks current administrator authority. Equal timestamps sort by ascending source then descending revision; pages read current retained history rather than one frozen snapshot.

Parsed, authenticated `saveMember`, `setStatus`, `reply` and `saveDrivePermissions` requests retain queued business denials in the separate `enterprise_office_request_denials` version 1 domain. Each record contains only a monotonic revision, authenticated employee, server-selected action, validated target ID, time and one of `forbidden`, `not_found`, `conflict`, `invalid_input` or `unauthenticated`. A session revoked while waiting retains its initially authenticated initiator; missing or invalid initial identity is never guessed. Malformed requests, other methods and infrastructure failures are outside this ledger. Request content, credentials and error text are never retained.

The denial write stays inside the existing mutation queue and completes before the original business rejection is returned; it changes no rejected business data and publishes no business success. Shutdown drains admitted writes. Entry or byte capacity retains all prior records and rejects further denial writes. A failed denial write returns safe HTTP `503 unavailable` with a fixed server warning; the business operation stays denied and its audit is unconfirmed. Restore storage or increase the configured capacity before retrying. Back up this domain with its original employee directory; startup refuses missing actors or invalid history. The six-source administrator search and NDJSON export do not include this separate ledger.

An employee reads items they created, own or participate in; administrators read all items. Hidden and absent items return the same `not_found` error. Only an organizer or administrator changes a meeting's status. Invitees answer only their own invitation. Inactive members cannot read or mutate data, including operations queued before their removal takes effect. Editing contact fields cannot change authorization roles.

Time decisions use one server observation in the saved company timezone. A task or to-do with a time expires at that exact local instant; without a time, it expires at the following local midnight. Calendar-day arithmetic preserves 23- and 25-hour days. Repeated wall-clock times use the earlier offset; nonexistent local instants require review. Dates retain the existing 0000–9999 range, and untimed work on 9999-12-31 requires an explicit time rather than overflowing its next-day deadline. Completed, cancelled, archived and deleted work is never unfinished overdue. Meetings derive upcoming, ongoing and ended phases separately from their saved status.

Only authorized items receive time decisions, including retained inactive work already readable by that employee. A known invalid stored time produces an item-only review marker; other items remain available, while unexpected infrastructure failures still reject the read. Reads do not change item status, persist time decisions or schedule reminders. The optional projection lets older servers retain their existing workbench interface.

Central reminders require explicit `reminders` configuration on the authoritative Office service. Omission opens no reminder domain, starts no reminder timer and omits `view.reminders`. One owned poll waits for its previous scan to settle before scheduling again, and scans share the business mutation queue. Work due reminders target only the current active assignee. Meeting start reminders target the active organizer and current pending or accepted invitees; declined, removed or inactive employees and ended meetings receive nothing. Occurrences outside the catch-up window, closed or inactive work and unresolved company times are not delivered. This service does not create Native scheduled prompts or external messages.

The independent `enterprise_office_reminders` version 1 ledger deduplicates each item, reminder kind, occurrence instant and recipient across restarts. Content edits, status progress and invitation replies do not create another reminder for the same occurrence. A changed deadline or recipient is evaluated on the next scan; an old occurrence is not delivered to a former assignee. Recipient views expose only current eligible authorized items, derive their titles from those items and hide obsolete reminders after completion, cancellation, archive, deletion, rescheduling or loss of recipient eligibility. Meeting reminders disappear when the meeting ends. `markReminderRead` acknowledges only the current recipient's visible UUID; repeating an acknowledged UUID writes nothing, and hidden or other-recipient IDs return `not_found`, including for administrators.

Entry and byte limits apply to the complete retained ledger before a whole scan batch commits. Capacity does not prune read or obsolete occurrence identities. Capacity or storage failure publishes no partial delivery; a fixed warning identifies the affected reminder operation and storage or capacity recovery. A later poll safely retries uncommitted occurrences within the catch-up window. Observer failure cannot undo a committed batch. Disabling configuration or unloading stops new polls and drains admitted writes before domain closure; a committed in-flight row remains retained without a late notification during shutdown. Re-enabling restores deduplication and read state. Back up this domain with its original employee and item directory; invalid, detached or over-capacity history rejects startup.

Organizers and administrators can edit an open meeting's title, date, time, location, notes and invitees using its reviewed revision. Its identity and organizer remain unchanged, and the organizer always participates. Omitting `inviteeIds` preserves membership; an empty array removes other participants. Newly added members must be active and receive invitations. Removed ordinary members lose meeting access and receive the previous title in a removal notice, including when the same edit renames the meeting. Retained replies survive member edits; date or time changes reset invitee replies to pending. Item, notifications and audit commit together. Closed, unauthorized and stale edits publish nothing; unchanged content and membership perform no write. New audit and notification kinds require the coordinated deployment described in the [membership upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-schedule-members/guide.md).

An assignee may accept a pending task into progress or reject it with a reason. The assignee, creator or administrator may transfer an open task to a different active employee with a reason; the task returns to pending. Each decision checks the reviewed item revision and current authority inside the write queue, retaining action, actor, time, reason and old/new owners with the task. Item, recipient notifications and audit commit together. A former assignee loses task access after transfer but retains the notification's title snapshot. Ordinary status edits remain available and preserve decision history; to-dos reject accept/reject decisions and meetings use separate controls. Follow the [task upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-task-decisions/guide.md) before using these actions with an older office reader.

The same transfer operation reassigns an open to-do to a different active member and resets it to pending. Assignees, creators and administrators use the reviewed revision and provide a reason. Its identity, content and deadline remain; separate to-do assignment history survives later content/status edits. The item, `todo_reassigned` notifications and audit commit together. The former assignee loses access while retaining the notice's title. The [to-do upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-todo-assignment/guide.md) defines coordinated deployment and older-reader refusal.

Creators, assignees and administrators may edit an open task or to-do's title, description, local date and optional due time on its reviewed revision. Omitting time clears the deadline's time of day. Identity, kind, status, assignment and decision history remain unchanged. An unchanged input performs no write; changed content commits the item, `work_updated` notifications and audit together. Meetings use their separate editor. The [work-edit upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-work-edits/guide.md) defines coordinated deployment before these new notification and audit kinds are stored.

`OfficeWorkPriority` supports low, normal, high and urgent. Existing and newly created work defaults to normal; creation and native tool arguments retain their existing contract. `updateWork` accepts an optional priority: omission preserves the stored value, while explicit normal removes a non-default value. A semantic priority change commits `work_prioritized` notifications and audit with the item. Unchanged priority writes nothing. Priority does not change date/time ordering or assignment history. Deploy according to the [priority upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-work-priority/guide.md) before storing these new discriminators.

Private human messaging uses a separate `enterprise_office_chat` domain. `chat` returns only the caller's conversations, including for administrators, and up to 100 messages before an exclusive sequence cursor. `sendMessage` requires a client UUID: retrying the same sender, recipient and text returns the committed message without duplication. `readChat` accepts only a cursor from that exact participant pair. Names retained on messages allow an active employee to read their own history after a peer is deactivated; new sends to that peer fail. Chat writes share the membership mutation queue, publish only after durability and drain before unload. Missing office-directory data alongside saved messages fails closed instead of reseeding another company over those messages.

Unsent drafts use the separate `enterprise_office_chat_drafts` version 1 domain. `chatDrafts` exposes only the authenticated employee's text and contact versions; administrators have no bypass. `saveChatDraft` accepts a reviewed version and a UUID retry identity. An exact retry returns the committed version; a stale window receives `conflict`. Empty drafts keep a version tombstone so a stale window cannot resurrect cleared text. Draft-change events contain no text, and all private projections recheck active membership. Existing work and chat domain schemas remain unchanged.

Mutations resolve after storage commit and revision notification dispatch. Failed validation, stale item revisions and authorization denials leave business data unchanged. Backend write errors propagate without publishing success. A failing notification observer is logged and does not reject a committed operation or prevent other observers from running. Shutdown rejects new work immediately, drains admitted mutations and closes every office domain.

Trusted server adapters can initialize password sign-in once for an existing administrator, enroll employees, issue durable sessions, revoke own sessions and change passwords. Passwords require 15–1024 characters and use independent random salts with scrypt (`N=131072, r=8, p=1`), following the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [Node crypto contract](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). Only token hashes enter the separate `enterprise_office_identity` domain. Sessions expire after eight hours, with at most five per employee. Resetting or changing a password revokes all previous sessions. Every authentication resolves current membership and role; reactivating an employee removes pre-offboarding tokens. Once sign-in is initialized, at least one active administrator must retain credentials. Bootstrap values never reset an existing password. The separate [office gateway](../office-gateway/README.md) supplies HTTP authentication and an explicit office-only operation list. Session-bound requests are rechecked when queued writes execute, so a revoked token cannot authorize a later write. Native Agent capabilities remain in the employee's own Host.

Internal meeting busy sharing requires explicit `scheduleAvailabilityEnabled: true` on the office service; its default is false. Active employees can query up to 500 active coworkers over one office-local date and interval. The read-only response returns unique member ids, busy flags, office timezone and observation time, without meeting identities or content. Open meetings with pending or accepted attendance count as busy; declined, completed, cancelled and adjacent meetings do not. Excluding a meeting requires current read access to it. Tasks and external calendars are not included. Results neither reserve time nor restrict otherwise authorized saving. The local workbench patch explicitly enables sharing; configure this policy on the central office service for gateway deployments.

Tasks and to-dos can retain up to 100 subtask checklist entries. Their creator, current assignee or an administrator replaces the list using the reviewed parent revision. Null input ids receive server-generated identities; retained ids must belong to this item. Entries inherit the parent permissions and are not independent assignments. Completing entries preserves parent status, priority, deadline and task-action history. Unchanged lists perform no write; closed, unauthorized and stale edits publish nothing. Changes commit the list, `work_subtasks_updated` notices and audit atomically. Follow the [subtask compatibility guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-work-subtasks/guide.md) before editing shared data.

Task delivery is explicit: the assignee submits an in-progress task, and its creator or an administrator confirms or returns the submission. Every action retains a nonempty explanation, actor, then-current assignee, time and item revision. A pending submission must still match the current item revision and assignee; any work edit, checklist change, transfer or status change requires resubmission. Confirmation completes the task; return keeps it in progress. After first submission, ordinary status changes cannot complete that task. Existing tasks without delivery history retain their status operations. History, notifications and audit commit together. See the [delivery upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-task-delivery/guide.md) before shared deployment. To-dos and meetings do not have task delivery review.

## Understand the implementation

Company announcements use `enterprise_office_announcements` version 1. Only active administrators publish plain text or withdraw a reviewed publication; one commit stores its immutable text and current active-employee recipient snapshot. A company-wide publication does not automatically reach later hires. Selected recipients must be active. Stable UUID retries return the original publication; changed payloads with a reused UUID reject. Recipients acknowledge only their own active deliveries, and repeat acknowledgements do not write again. Withdrawal hides the publication from recipients while retaining its author, text, withdrawal actor/time and read receipts. Administrators can manage retained publications; ordinary projections exclude other recipients and receipts. Existing work, chat, identity and Session schemas remain unchanged. Empty change events prompt authorized reads; failed storage publishes no success, and observer failures cannot undo a committed operation.

Company integration registrations use `enterprise_office_integrations` version 1. Active members read descriptive manifests in the office view; only current administrators call `importIntegration`. The strict JSON object requires `name`, `system`, `version`, `provider`, `description` and 1–30 unique `capabilities`; `owner` is optional. Import measures the full UTF-8 envelope against 256 KiB and rejects unrecognized fields, including endpoints, credentials and code. Names are normalized and compared without case; a collision returns `duplicate_name`. Exact UUID/text retries return the saved registration. One commit stores the catalog and import audit; an empty change event prompts fresh reads. Up to 1,000 registrations are retained. Import never installs a native plugin or verifies connectivity, and retained data with a missing original directory fails closed.

Formal organization is opt-in through the administrator's Team page. The first-configuration wizard displays the configured company and timezone, then requires review of current member department and job labels before adopting them into `enterprise_office_organization` version 1. `initializeOrganization` checks the reviewed directory revision and never reseeds an initialized organization. `OfficeOrganizationUnit` and `OfficePosition` have opaque UUID identities and independent revisions; `OfficeOrganizationAssignment` links retained employees to a department and a global or department-scoped position. Cycles, duplicate sibling names, stale writes and incompatible positions are rejected. Active employee affiliations and active child entities must be cleared or reassigned before deactivation. Administrators retain inactive history; employee projections hide inactive entities and affiliations.

`saveOrganizationUnit`, `savePosition` and `assignOrganization` require a current active administrator inside the shared write queue. Personal profile changes cannot move formal affiliations, and positions confer no account role or file permission. The original member schema and contact labels remain intact for old records and reviewed member edits. Organization notifications contain no business payload; clients reload their authorized view. During whole-Host shutdown, a storage-facility drain barrier prevents sibling plugin teardown from closing domains before admitted office operations reach durability.

The `drive`, `createDriveFolder`, `renameDriveEntry`, `saveDrivePermissions`, `uploadDriveFile` and `downloadDriveFile` methods use a separate `enterprise_office_drive` version 1 unit. Private roots are employee-specific, with no administrator read bypass. Shared roots start read-only for employees and editable for administrators; individual shared entries then follow owner/default/account conditions at every ancestor. A hidden ancestor blocks even a child owner's access. Permission grants use administrator-managed member ids, never self-edited department labels. Case-insensitive sibling names and Windows filename rules apply; mutations require current entry revisions, recheck membership in the shared queue and publish only after durable metadata/audit commit.

Drive bytes live in exclusive immutable objects below `DSH_HOME/office/drive/v1/objects`, with a server UUID, size and SHA-256 in metadata. Bytes are fsynced before metadata publishes. Reads are bounded and verify size and digest before returning content. An exact upload UUID/payload retry returns the original entry; a changed payload conflicts. Back up both this object tree and the configured `enterprise_office_drive` storage unit. A metadata failure can leave an unreachable object; automatic orphan collection is deferred so an uncertain commit never causes referenced bytes to be deleted.

The `enterprise_office` version 1 domain stores one complete business commit. Items, participation, recipient notifications and audit records change together; the JSON backend atomically rewrites that unit. The service serializes read-modify-write operations and checks authority within that sequence. Per-item revisions reject stale edits. A disposable worker with an empty environment parses each read; cancellation, timeout and shutdown terminate it before settlement. The final ownership, role, ancestor-permission and version check and bounded result occur in the same office queue. No complete-document cache or native attachment copy is retained; parsing and limit failures return no body.

`readConversationXlsx` reads saved `.xlsx` cells without recalculating formulas. `sheetNumber` follows workbook order from 1, independent of sheet ids; `offset` counts stored cells, including explicit blanks, in row/column order. A read returns at most `maxCells` (1–256), the bounded worksheet directory, addresses, hidden sheet/row/column states and continuation. Sparse gaps and merged ranges do not create cells. Numeric values and date serials remain exact XML lexical strings in `value` and `rawValue`; `dateSystem` identifies the 1900/1904 epoch, and `numberFormat` supplies the saved format without visual formatting. For shared strings, `rawValue` is the saved string-table index; booleans retain `0`/`1` there. XML string entities are decoded once. No JavaScript numeric approximation replaces the source amount or serial.

Formula evidence retains the original XML text, type, shared index and range; shared references are not expanded into invented expressions. `cacheState` distinguishes `missing` from `present_may_be_stale`, including saved zero, false and empty-string results. A saved result is never reported as recalculated. [OOXML cell values](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.cellvalue) define stored values and formula caches; [ExcelJS](https://github.com/exceljs/exceljs#formula-value) does not calculate them. The reader rejects macro-enabled content, VBA, external workbook dependencies, data connections, DTD/entity declarations and ambiguous package parts. Hyperlinks return existing display text without returning or fetching their targets. Charts, drawings, images, comments, pivot tables, Table styling, old `.xls`, `.xlsb`, `.xlsm` and encrypted workbooks are outside this reader.

`conversationXlsx` bounds compressed bytes (8 MiB), all ZIP entries (2,048), total declared expansion including skipped media (32 MiB), each XML/relationship/VML part (8 MiB), XML nodes (500,000), worksheets (32), stored cells across all sheets (100,000), extracted values/raw values/formulas/formats/names (1 Mi UTF-16 code units), complete escaped native tool-content JSON bytes (64 KiB), worker deadline (5,000 ms) and V8 old-generation heap (256 MiB). ZIP/XML budgets are checked before ExcelJS loads the workbook. Its bounded transient parser copy omits DrawingML and binary media and exists only inside the worker. The service checks input size before full allocation, verifies actual bytes and SHA-256 before creating the empty-environment worker, and awaits worker termination on failure, cancellation, timeout or shutdown. The final ownership, role, ACL and latest-version check and complete-result limit share the office queue without an intervening await. A cell or directory that cannot fit returns no result; values and formulas are never truncated. No complete-document cache or native attachment copy is retained.

`readConversationPptx` reads saved `.pptx` shape text, grouped shapes and table cells in source order. `slideNumber` follows the presentation relationship list from 1; `section` must explicitly select `slide` or `notes`. Notes are never appended automatically, and page/date/header/footer/image placeholders in notes are excluded. The result includes the bounded slide directory with hidden/notes flags, selected-section paragraph/table/hidden-shape counts, verified file metadata, `text`, `nextOffset` and `eof`. Hidden shape text remains included. UTF-16 windows never exceed `maxCharacters` (1–16,384), back up before a surrogate pair and fail when the next complete character cannot fit. Images, charts, SmartArt, master/layout text, attachments, visual layout, OCR and old `.ppt` are outside this reader; macros, malformed relationships and unsafe ZIP/XML fail without text. External hyperlinks remain inert.

`conversationPptx` is optional and disabled when omitted. Enabling it requires every limit explicitly: `maxBytes`, `maxArchiveEntries`, `maxInflatedBytes`, `maxXmlBytes`, `maxNodes`, `maxSlides`, `maxTextCharacters`, `maxOutputBytes`, `timeoutMs` and `workerMemoryMb`. Limits cover compressed input before full allocation, all declared expanded ZIP bytes including ignored media, every parsed XML part, visited nodes, all ordered slides and their body/notes text, and the complete escaped native result including file/directory metadata. Each actual read verifies submitted ownership, current employee/role, ancestor ACL, latest immutable version and full SHA-256 before its empty-environment worker. It rechecks current authority and version in the same queue before publishing the bounded result. Cancellation, timeout and unload await worker termination; no full-document cache or native attachment copy is retained.

The optional `conversationFiles.pdf.maxBytes`, `conversationFiles.docx.maxBytes`, `conversationFiles.xlsx.maxBytes` and `conversationFiles.pptx.maxBytes` capabilities independently enable their formats within the current authority's input limits; omission leaves that format unavailable. Older authorities without these capabilities retain text-only selection. Native tool consumers preserve their original approval and durable result pipeline.

### Agent work execution

`createWorkFromConversation` accepts an `OfficeAgentWorkInput`: a UUID execution retry id, a private prepared capture and ordinary task/to-do fields. It creates only an internal office item and its existing assignee notification; it sends no external company-system request. New writes require an active employee and assignee, the capture's original employee and current role, the same reviewed association version, and a selected `template:reminder`. Current declared requirements must match the capture, be registered and remain linked. Required connections must be enabled, policy-admitted, available and at the captured version. Readiness is not a claim of successful external delivery.

The independent `enterprise_office_agent_work` version 1 domain reserves a server-issued item UUID before the ordinary work commit. If reservation persistence fails, no business item is written. If the business write or acknowledgement fails afterward, an exact retry recovers the same reserved item rather than creating another. Pending reservations recheck current authority before a new write, including adapter disposal during reservation persistence. Completed retries are authorized reads of the original item even after unlinking; they do not execute again. `OfficeAgentWorkReceipt` returns the request coordinates, reservation time and current authorized item state. Changing the payload under an existing execution id conflicts.

Retention counts compact reservation JSON including work fields and fingerprints; lowering bounds preserves exact retries. Full retention reports `conflict` without a new business write. Back up this domain with work data and prepared captures. Corrupt fingerprints or a missing original directory refuse startup. The shared office queue and shutdown drain own both reservation and business publication. The [reservation decision](../../../.agents/notes/implemented/architecture/2026-10-17-office-agent-work-reservations.md) explains recovery across those two commits. Native model-tool exposure is a separate consumer; ordinary manual work creation retains its existing API.

### Drive version history and recovery

`OfficeDriveView.lifecycle` advertises reviewed file replacement, version history and soft deletion. An optional upload `target` fixes the file id and revision alongside its current name and location. Authorized editors can upload replacements; original ownership and conditions remain. Each chunk and publication rechecks current access and the reviewed revision. Historical and deleted versions continue consuming the file owner's quota; pending replacements by other editors reserve that same owner's capacity. Exact retries include the target and retain their original identity. `driveHistory` returns newest-first version metadata without upload retry credentials; `driveVersionInfo` verifies a selected object's complete integrity, and `downloadDriveRange` reauthorizes every historical range.

`changeDriveLifecycle` requires ownership, current parent edit permission and the reviewed revision. Deleting a folder hides all descendants without discarding their records or bytes. `driveTrash` lists only this owner's deleted roots through currently visible parents. Restoration preserves ids, conditions and versions; sibling conflicts reject unless the owner supplies a valid new name. These operations retain existing Native Session and delivered-file data. Follow the [version upgrade guide](../../../docs/upgrade-guide/v0.2.1-alpha.2/office-drive-versions/guide.md) before writing replacement or cleanup receipts to shared storage.

`drivePurgePlan` reviews an exact deleted subtree owned entirely by the caller, excluding already completed cleanups. Confirmation through `purgeDrive` requires the same revision and digest, a stable request id and current parent edit access. The service durably records irreversible authorization before unlinking its own opaque Drive objects; Native paths are never deletion targets. A failure retains a pending receipt, prevents restoration and keeps the byte charge. `drivePurgeStatus` reads the owner's prior receipt; `retryDrivePurge`, startup recovery and `drivePurgeSweepMs` maintenance continue only an existing approval. Exact confirmation retries are idempotent. Only a durable completion releases byte quota; retained audit tombstones remain subject to the metadata count limit. `OfficeDriveView.quota` reports the employee's used, reserved and configured bytes. The browser confirmation flow has a separate UI owner.

## Known Limitations and Deferred Work

- Password authentication primitives live here; the separate gateway owns network ingress. SSO, directory synchronization and multifactor authentication remain pending.
- The current storage unit and write sequence have one Host owner. Concurrent writers in separate Hosts require a transactional provider or central service; sharing a JSON file does not provide that coordination.
- Whole-unit commits grow with history. Chat reads have cursor pagination; work-list pagination, retention and scalable enterprise storage remain pending.
- Administrator audit search covers six retained operation histories and the four authenticated mutation RPCs' denial ledger. Other authorization denials, private external execution stages and usage accounting are not aggregated. Identity, organization and connection histories retain at most 1,000 entries each; exports cannot recover discarded entries.
- Whole-request file transfers and chat files retain an 8 MiB envelope. The resumable drive service defaults to 64 MiB files and a configurable 256 MiB file-owner quota; its browser flow has a separate UI owner. General collection of older whole-upload orphans remains pending. Permanent cleanup retains metadata and audit tombstones within the existing directory-count limit.
- Meetings cover one local calendar day. Recurrence, automatic reminders, external calendar availability/delivery, time reservation and multi-day events remain separate work.
- This package provides office records, configured connection probing, declared business reads and a controlled write coordinator. The UI has its own package with reviewed business forms; group chats and customer-adapter commissioning remain pending. The external write ledger alone grants no execution authority.
- OA bridge v1 requires a customer bridge and its actual API, identity and authorization agreements. It accepts declared text fields; attachment upload, arbitrary request-id queries, approval decisions, callbacks and automatic synchronization are outside this adapter. Accepted submission receipts do not mean business approval.

### Dev Note

Immutable transfer writes serialize each file's publication through temporary-handle close and cleanup within one service instance; independent files keep separate queues. Exact retries verify the completed object, and a failed publication releases subsequent attempts without masking its own failure. Windows queue identities include case-equivalent paths. Cross-process changes still face exclusive publication and the existing size, digest, file-identity and metadata checks; a detected change remains a conflict requiring retry.

Domain cleanup is registered before initialization opens its first handle. Each completed open is owned explicitly; a handle that arrives after unload is closed before it can publish a service. Shutdown still drains admitted mutations and attempts every owned domain close even if another close fails. The composition tests cover unloading during a delayed first open and activating again in the same storage facility.
